# Personal Model Benchmark — 設計稿 v0.2

> 目的：新模型一出來，用任一 coding agent（Claude Code / Codex / Gemini CLI / agy …）選該模型直接跑，
> 跑完拿到「**在我的工作型態上**」可跨模型比較的成績單。
> 狀態（2026-10-14）：第一批 6 題（R06、X01、X03、C01、C03、J01）與 `bench.py` 已完成並通過 selftest；其餘題目依第 8 節順序建置。
> v0.2 變更（2026-10-14）：① 全部改為**抽象化 + 合成資料**，本 repo 不放任何真實機密或個人資訊；
> ② 評分固定「先客觀、後評審」，評審模型後定；③ 依各 repo 的 skills 拆出「能力原子」重新出題，補上讀書彙整、寫作、PPT、Excel 等類別。

## 1. 設計原則

| 原則 | 做法 |
|------|------|
| **零真實資料** | 不複製任何 repo 的內容進來。每題只抽「工作型態」，輸入全部是合成的：虛構公司、虛構人名、虛構客戶、自寫的書章與素材、程式產生的 Excel / CSV。`bench.py lint-data` 掃描禁用詞表（存在本機、不進 repo）防誤入 |
| **一個虛構世界** | 共用一份 `world/`：虛構公司「澄岳科技」三條產品線、10 位虛構同事、2 個虛構客戶、半年的事件時間軸。PM 類題目因此有前後文可續寫，又不碰真資料 |
| **能力原子化** | 一題只測一個能力（讀一章、改一篇稿、建一個 Excel…），方便定位「新模型哪裡變強 / 變弱」；另有少數「串接題」測多步工作流 |
| **預埋答案** | 合成輸入時就埋好可檢查的東西：必須抓到的重點、必須抓出的錯、必須保持不變的檔案、必須拒絕編造的空缺。客觀分就是對這些埋點計分 |
| **先客觀、後評審** | 第一段 `check.py` 純程式評分；第二段才交 LLM 評審，且只評客觀分量不到的品質（可讀性、觀點、取捨）。評審模型未定前，只出客觀分 |
| **跨 agent 同一份輸入** | 任務 = 資料夾 + `PROMPT.md`；作答規則寫在 `AGENTS.md`，`CLAUDE.md` / `GEMINI.md` 橋接，不依賴特定 agent 功能 |
| **無人值守** | 作答中不准問人；不確定就寫進 `NOTES.md`（假設 / 待確認）。「該標待確認卻硬做」是計分項 |

## 4. 評分流程（先客觀、後評審）

```text
grade
 ├─ 第 1 段 客觀（check.py，每題輸出 items[]：名稱、權重、得分、證據）
 │    ├─ 埋點命中 / 精確比對 / 隱藏測試 / schema
 │    ├─ 紀律：工作區外檔案、唯讀檔、測試檔是否被改（以 new 時的 hash 清單比對）
 │    └─ 誠實：數字 / 專名追溯失敗 → 扣分（防編造）
 ├─ 第 2 段 評審（僅限有「評審」欄的題目）
 │    ├─ 評審模型寫在 graders/judge.yaml；留空 → 跳過，報表標「待評審」
 │    ├─ rubric 每項有 1 / 3 / 5 分錨點 + 參考答案；評 2 次取平均，差 > 1 分標人工複核
 │    └─ 客觀分 < 40 的作答不送評審（先過及格線再談品質）
 └─ 第 3 段 人工（選填）：每題「我會不會直接用」1–5 分
```

- **每題分數**：有評審項的題目＝客觀 70% + 評審 30%；評審未跑時只顯示客觀分，不估算。
- **總分**：七類加權（R 20 / W 20 / D 15 / P 10 / X 10 / C 15 / J 10），報表永遠並列分類分數。
- **過程指標**：耗時、token / 費用、是否中途卡住需人介入、`NOTES.md` 中的待確認項是否合理。

## 5. 執行方式

```text
python bench.py doctor                      # 檢查 Python / Node / 套件與各 agent CLI
python bench.py new  --agent codex --model <新模型> --suite quick
python bench.py run  runs/<id>              # 無頭模式：逐題呼叫 claude -p / codex exec / gemini -p，自動計時、存 log、抓 token
python bench.py grade runs/<id>
python bench.py board                       # results/leaderboard.md
```

- **無頭模式（建議）**：`bench.py run` 在每題資料夾內呼叫 agent 的非互動指令，一題一個乾淨 session，避免前面的題目吃掉後面的 context；agent 與模型參數由 `agents.yaml` 設定，新增 agent 只要加一段指令範本。
- **互動模式**：在 `runs/<id>/` 開 agent，說「依 TASKS.md 全部做完」。測的是長 session 下的表現，適合不支援無頭模式的工具。報表會標註模式，兩種模式分開排名。
- **防偷看**：作答資料夾不含 `graders/`；每題輸入埋一個 canary 字串，評分器的參考答案也有，若作答中出現評分器專屬的 canary 即判作弊。

## 6. 合成資料策略

| 類型 | 做法 |
|------|------|
| 虛構世界（`world/`） | 公司、產品線、人物、客戶、時間軸寫成 YAML；PM 類題目的文件由它衍生，前後一致 |
| 書章 / 素材 / 文章 | 由我撰寫的原創內容，主題貼近你的閱讀範圍（Agent 工程、資料平台、產品管理），埋點清單寫在 `graders/<task>/plants.yaml` |
| Excel / CSV / PPTX / git repo | 以 `generators/*.py`（固定 seed）產生，產生器與輸出都進 repo，可重現 |
| 程式專案 | 原創的小型專案，模仿你常見的程式結構（排程、時區、季度、索引、notebook cell），附參考解答與隱藏測試 |
| 參考答案 | 每題一份人工確認過的參考解答，同時用來驗證 `check.py` 本身（參考解答必須拿到 ≥ 95 分，空作答必須 ≤ 5 分） |
| 防誤入 | `bench.py lint-data` 用本機私有禁用詞表（真實人名、客戶、內部代號）掃整個 repo；該詞表在 `.gitignore` |

## 8. 建置順序

1. `bench.py` 骨架（doctor / new / run / grade / board）+ 作答規則 + `world/`。
2. 第一批：全客觀、最能驗證流程的 ★ 題：C01、C03、X01、X03、J01、R06。用現有模型跑一次當基準。
3. 第二批：補齊 quick suite 其餘 ★ 題（R01、R03、R04、W01、W02、D01、D03、P01、P02），含評審 rubric（評審模型待定，先只跑客觀）。
4. 第三批：full suite 與串接題。
5. 每季：新增 2–3 題反映新工作型態，舊題保留做長期比較。
